# 知识库 Pipeline 索引失败状态修复规格

## Problem Statement

用户上传文件后，知识库页面长期显示“排队中”。实际运行证据表明，发布版知识库 Pipeline 已被 Worker 消费，但知识索引节点因为历史配置中的 `summary_prompt=null` 无法通过数据校验。任务内部记录异常后仍被外层当作成功完成，关联文档没有进入错误状态，导致文档永久保持 `waiting`，用户无法判断失败原因，也无法通过既有错误文档重试入口恢复索引。

## Solution

在运行时兼容空或缺失的摘要 Prompt，使其继续使用系统既有的默认 Prompt；不回写历史 Workflow 或知识库配置。同时，统一处理发布版知识库 Pipeline 的执行异常：在确认租户、知识库、Pipeline 与文档属于同一业务边界后，将文档标记为 `error`，保存面向用户的简化错误信息，并将完整异常堆栈保留在 Worker 日志中。失败不自动重试，由用户通过既有手动重试能力重新发起索引。

## User Stories

1. 作为知识库使用者，我希望上传文件后，摘要 Prompt 为空时仍能继续索引，以便历史配置不会阻塞新文件。
2. 作为知识库使用者，我希望摘要索引仍然保持启用，以便兼容处理不会静默关闭已选择的能力。
3. 作为知识库使用者，我希望有效摘要 Prompt 的行为保持不变，以便升级不会影响现有索引结果。
4. 作为知识库使用者，我希望 Pipeline 初始化失败时看到“失败”而不是“排队中”，以便准确判断当前状态。
5. 作为知识库使用者，我希望失败文档能显示简洁、可理解的失败原因，以便采取修复措施。
6. 作为知识库使用者，我希望失败后可以手动重试，以便在修复配置或外部依赖后重新建立索引。
7. 作为知识库使用者，我不希望系统自动重复执行失败任务，以便避免重复写入分片、向量或图索引。
8. 作为知识库使用者，我希望普通 Workflow 执行不会改变知识库文档状态，以便不同业务流程的状态语义保持隔离。
9. 作为租户管理员，我希望一个租户的 Pipeline 异常不能修改其他租户的文档，以便保证租户隔离。
10. 作为知识库管理员，我希望一个知识库的 Pipeline 异常不能修改其他知识库的文档，以便保证数据边界正确。
11. 作为知识库管理员，我希望 Pipeline 不匹配时不会误更新文档，以便避免错误任务影响其他 Pipeline 的索引。
12. 作为运维人员，我希望 Worker 日志保留完整 traceback，以便在页面简化错误信息后仍可定位根因。
13. 作为运维人员，我希望任务失败后 Celery 成功日志不再掩盖文档失败状态，以便监控和页面状态保持一致。
14. 作为升级维护人员，我希望历史空 Prompt 只在运行时兼容，以便不需要批量修改生产 Workflow 数据。
15. 作为升级维护人员，我希望修复范围不扩展到前端配置页面，以便降低升级冲突和回滚风险。
16. 作为知识库管理员，我希望当前已确认卡住的文档能够单独恢复为可重试的错误状态，以便不必重新上传源文件。

## Implementation Decisions

- 摘要 Prompt 的空值和缺失值在运行时归一化为可被现有默认 Prompt 逻辑处理的形式。
- 不增加数据库字段，不修改 Workflow 持久化数据，不执行历史配置批量迁移。
- 发布版知识库 Pipeline 的异常处理覆盖节点创建、解析、模型调用、向量写入和图索引等执行阶段。
- 只有在调用来源为发布版知识库 Pipeline，并且租户、知识库、Pipeline、文档四项关系校验通过时，才允许回写文档状态。
- 失败状态写入 `error`；已经完成的文档不能因迟到的异常回写被降级。
- 文档错误字段只保存简化后的业务错误信息；完整异常对象和 traceback 只记录到 Worker 日志。
- 失败任务不自动重试；重试由既有人工入口触发，并沿用已有的执行日志和重试链路。
- 当前已确认卡住的目标文档只执行一次范围限定的 `waiting` 到 `error` 状态修复；不扫描其他历史 `waiting` 文档。
- 不改变普通 Workflow 的错误处理和文档状态语义。
- 保持 priority Pipeline 和普通 Pipeline 两条任务队列的行为一致。

## Testing Decisions

- 测试只验证外部行为和业务状态，不锁定具体异常堆栈文本、线程实现或内部调用顺序。
- 在知识索引节点数据校验层覆盖：摘要 Prompt 为 `null`、摘要 Prompt 缺失、摘要 Prompt 为有效字符串、摘要索引关闭，以及已有的 `enable=null` 兼容场景。
- 在发布版知识库 Pipeline 任务层覆盖：节点初始化异常、执行阶段异常、文档关系匹配、租户不匹配、知识库不匹配、Pipeline 不匹配、普通 Workflow 调用，以及错误信息简化和完整日志记录的边界。
- 覆盖 priority 队列和普通队列，确保两条入口都遵守相同的文档状态规则。
- 覆盖手动重试前后状态：失败后为 `error`，重试入口可以将任务重新提交，不由失败任务自动触发第二次执行。
- 覆盖已完成文档的状态保护，避免迟到异常将其降级为 `error`。
- 复用现有知识索引节点单元测试和 Pipeline 任务测试基础；只有现有 seam 无法观察文档状态时，才增加最小的任务状态测试 seam。

## Out of Scope

- 前端摘要 Prompt 配置控件和保存逻辑。
- 新增错误码、数据库字段或 API 返回结构。
- 自动修复或批量迁移历史 Workflow 配置。
- 自动重试、定时补偿和失败任务死信队列。
- 全量扫描历史 `waiting` 文档。
- 普通 Workflow 执行失败后的统一文档状态改造。
- Neo4j 数据清理、图索引重建策略或召回排序策略调整。

## Further Notes

## 新增生产证据（2026-07-22）

- Worker 日志再次确认：`qwen3.6-35b-a3b-mtp` 因近期失败进入 cooldown，模型调用返回 HTTP 503。该日志对应数据集 `d6bcac3f-9442-463e-9e10-fd18720fb273`，不是本规格中的目标数据集，不能直接作为目标文档的根因。
- QA 索引处理器在模型调用失败时只记录 `Failed to format qa document` 并继续返回空 QA 文档，外层任务因此记录为 `succeeded`，形成“任务成功但索引内容为空”的假成功。
- 修复方式：保留 Worker 的完整 traceback；在正式索引和预览路径收集 QA 格式化异常，线程汇合后将异常重新抛出，使既有 Pipeline 失败状态回写逻辑能够把关联文档标记为 `error`。
- 本地回归验证：QA 索引处理器及相关 Pipeline/RAG 测试共 `148 passed`；本轮两个文件 Ruff 检查通过。
- 生产部署、目标文档状态修复、手动重试和线上重新验证尚未执行；Qwen 模型服务的 503 cooldown 仍属于外部依赖风险。

- 本次生产证据中的失败发生在知识索引节点实例创建阶段，因此现有下游摘要生成默认值尚未生效；运行时归一化必须发生在节点数据校验通过之前。
- 任务层的异常回写应复用现有文档重试入口所依赖的 Pipeline 执行日志，不能通过创建新的上传文档来替代手动重试。
- 生产状态修复顺序应为：代码验证通过 → 部署并健康检查 → 仅将目标文档从 `waiting` 修复为 `error` → 用户手动重试 → 通过日志、接口和数据库只读状态确认索引结果。
- 当前未配置可用的项目 issue tracker，因此本规格以仓库内正式规格文档作为状态源；后续如配置 tracker，应同步发布并标记为 `ready-for-agent`。
